# Changelog

All notable changes to RustConn will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.24.10] - 2026-11-09
### Fixed
- **macOS: the menu-bar icon follows the system style** — the tray icon was a full-colour image that clashed with the other status items. It is now a monochrome template glyph, so macOS tints it for a light or dark menu bar like any native item. (`rustconn/src/tray.rs`, `rustconn/assets/icons/hicolor/scalable/apps/io.github.totoshko88.RustConn-tray-macos.svg`)
- **macOS: Settings no longer shifts and clips a few seconds after opening** — once client detection finished, the Clients page replaced its rows with full install paths and unbounded version strings, which made the dialog wider than its 600 px content width and cut off every page. The path is now one ellipsised line (full text in a tooltip) and the version label is ellipsised too. (`rustconn/src/dialogs/settings/clients_tab.rs`)
- **macOS: the Dock icon is grey in the Clear and Tinted icon styles** — when RustConn runs without a `.app` bundle, its Dock tile is set at runtime, which bypasses the system's monochrome icon styles, so it stayed full-colour next to every other app. The tile now reads `AppleIconAppearanceTheme` and, for Clear or Tinted, uses a grey tile (dark or light to match). Inside a bundle the `.icns` is still left to macOS. (`rustconn/src/main.rs`, `rustconn/assets/icons/macos-dock/`)
- **A broken CLI wrapper is no longer shown as installed with an error for a version** — Settings → Connection showed Tailscale CLI with a ✓ and `/usr/local/bin/tailscale: line 2: …: No such file or directory` in the version column when the wrapper outlived a removed Tailscale.app. A command that exits 126/127 (the shell's "cannot execute" / "not found") now yields no version and is reported as not found. Applies to every Zero Trust CLI on that page. (`rustconn/src/dialogs/settings/clients_tab.rs`)
### Changed
- **macOS: Compact interface is off by default** — it was switched on for new macOS installs to compensate for scaling problems that are now fixed. A fresh install gets the standard chrome, as on Linux. Existing users keep whatever is saved in their settings; the switch is still in Settings → Interface, the primary menu and `Ctrl+Shift+D`. (`rustconn-core/src/config/settings.rs`)
### Improved
- **Settings no longer spins the main loop while it detects clients** — the Clients and SSH Agent pages polled their background result through an idle source, which never sleeps, so the interface ran flat out for the few seconds detection took each time Settings opened. They now poll every 50 ms, as the Secrets page already did. (`rustconn/src/dialogs/settings/clients_tab.rs`, `rustconn/src/dialogs/settings/ssh_agent_tab.rs`)
- **Development builds optimise third-party dependencies** — `cargo run` compiled GTK, VTE and IronRDP at opt-level 0, which made tab overview, redraws and scrolling feel slower than a release build. Dependencies are now built at opt-level 2 in the dev profile; the workspace crates are unchanged. (`Cargo.toml`)
### Documentation
- **macOS: running with `cargo run`** — `docs/MACOS_BUILD.md` now shows the full `cargo run` command with the macOS feature set and explains why the default features fail on `javascriptcoregtk-6.0`. (`docs/MACOS_BUILD.md`)
### Dependencies
- **Updated** (semver-compatible): arc-swap 1.9.4→1.9.5, itoa 1.0.18→1.0.19, notify-types 2.2.0→2.3.0, syn 3.0.9→3.0.10. `cargo deny check advisories` is clean; CLI downloads, FreeRDP 3.33.0, cJSON 1.7.19, GNOME runtime 51 and Snap core26 are current.
- **RUSTSEC-2023-0071 (rsa Marvin Attack) — a fix now exists but is still out of reach** — rsa 0.10.0 (2026-11-08) is the patched release, with constant-time arithmetic. RustConn cannot take it yet: `ironrdp-connector` 0.12.0, the latest, pins `picky =7.0.0-rc.26`, and picky, sspi and winscard pin `rsa =0.10.0-rc.18`; the same pins hold sspi 0.23.1, winscard 0.4.1, picky rc.29 and pkcs1 0.8.0 back. The acceptance rationale in `deny.toml` and `.cargo/audit.toml` is updated to say so; it is not exploitable in a local client that exposes no RSA decryption oracle.
- **zbus 6 / oo7 0.7 deferred** — both are breaking releases (zbus 6 removes the blocking API and renames `Value` to `Variant`), and the Linux tray's `ksni` 0.3.7 is still on zbus 5, so moving now would build two zbus versions. Planned for when ksni follows.

## [0.24.9] - 2026-11-09

### Added
- **Azerbaijani (az) added — [PR #414](https://github.com/totoshko88/RustConn/pull/414), contributed by Naim Shafiev** — a full catalogue of this release's strings, with terminology aligned to the GNOME and Firefox Azerbaijani translations. (`po/az.po`, `po/LINGUAS`, `rustconn/src/i18n.rs`, `rustconn/src/app.rs`, `README.md`, `docs/INSTALL.md`)

### Fixed
- **The CodeQL scan runs again** — every job of the in-repo CodeQL workflow failed. Rust was set to the `autobuild` build mode, which CodeQL does not support for Rust (only `none`); the Python and Ruby jobs found no code, because the only Python and Ruby files live under `scripts/` and `packaging/`, which the config excludes; and the Actions job's results were refused because the repository's CodeQL default setup was still enabled. The workflow now scans `actions` and `rust` (build mode `none`), and default setup is to be turned off in Settings → Code security, as the workflow header now explains. The CodeQL change was contributed in PR #414 by Naim Shafiev. (`.github/workflows/codeql.yml`, `.github/codeql/codeql-config.yml`)

### Changed
- **Bitwarden's "Keep the CLI running" process now stops when the screen locks or the computer suspends** — with the switch on, one `bw serve` process holds the unlocked vault in its memory, and until now it stayed running while the user was away. It is now stopped on the same screen-lock and suspend signals that remove RustConn's SSH keys from the agent, on Linux and macOS. Nothing asks for the master password afterwards: the session key stays in RustConn, as it does with the switch off, so the next vault operation starts a fresh `bw serve` and only that first operation is slower. A process busy with an operation at that moment is stopped as soon as the operation finishes, so a lookup in flight is never cut off, and the stop never delays the lock or the suspend. In the Flatpak this needs the same opt-in `flatpak override` as the SSH key removal; in the Snap a screen lock is seen and a suspend is not. (`rustconn-core/src/secret/bitwarden.rs`, `rustconn-core/src/secret/bitwarden_serve.rs`, `rustconn-core/src/lock_events/mod.rs`, `rustconn/src/app.rs`, `docs/BITWARDEN_SETUP.md`, `docs/INSTALL.md`)

### Dependencies
- **resvg 0.48 → 0.49** — the SVG renderer for the tray icon (supersedes Dependabot PR #404). The calls RustConn makes (`usvg::Tree::from_data`, `resvg::render`) are unchanged in this release. (`rustconn/Cargo.toml`)
- **CI — taiki-e/install-action v2.87.25 → v2.88.1** (Dependabot PR #403), pinned by commit SHA as before, in every CI and release job that installs a Rust tool. (`.github/workflows/ci.yml`, `.github/workflows/release.yml`)

## [0.24.8] - 2026-11-08

### Added
- **Dynamic Folder scripts can define the full connection, not just host/port/username (issue #410)** — a dynamic-folder entry now accepts an optional `protocol_config` object in the native RustConn shape, so a generated connection can carry anything the connection editor sets: an SSH `startup_command` (e.g. `tmux new-session -A -s my-session`), an `auth_method`, RDP display options, and so on. The object is the same tagged form the config file uses (`{"type": "Ssh", "startup_command": "…", "auth_method": "agent"}`); its `type` tag decides the protocol and default port, and the `protocol` string is then only used to warn on a mismatch. Entries without `protocol_config` behave exactly as before, so existing scripts are unaffected. Because the connection stays read-only, the configuration is re-applied on every refresh instead of being lost when the folder regenerates, which removes the need to hand-edit a generated connection only to have the edit discarded on the next refresh. (`rustconn-core/src/models/dynamic_folder.rs`, `rustconn-core/src/dynamic_folder.rs`, `docs/USER_GUIDE.md`)
- **A KeePass database per connection or group (issue #411)** — with the KeePass backend, a connection or a group can now name its own `.kdbx` file instead of the single global one, so personal and corporate vaults can live side by side. Groups get a **KeePass Database** row on the Identity page (independent of Default Credentials); connections get one beside the Vault password source. A connection reads from its own file, else from the nearest group above it that sets one, else from the global database; an empty field inherits. Only the file changes — the database password, key file and YubiKey slot still come from Settings → Secrets, so a database that needs a different passphrase is not covered yet. The path is device-local: it is stripped from the full sync export, never part of Group Sync, and a remote edit keeps this device's own value. Switching a connection's password source away from Vault drops its path. The unlock prompt for a locked database now names the override file. Every KeePass operation follows the same resolution, not just the connect: saving, loading and testing a password in the connection editor, a group's own password (saved, loaded and deleted in the group's database), copying a connection's password on paste, deleting it with the connection, renaming it on an edit or group move, and the VNC password prompt. A move that changes which database a connection resolves to leaves the entry in the old file and logs it, rather than copying between databases; the password is entered again. The **KeePass Database** rows are hidden when the KeePass backend is not active, and the file picker filters on `*.kdbx` with a named filter. `rustconn-cli` follows the same resolution: `secret get`, `secret set`, `secret delete` and `add --password-stdin` open the connection's database instead of always the global one and print which file they used, and the override is set with `--kdbx-path` on `add`, `update` and `group edit` (an empty value on `update`/`group edit` clears it) and shown by `show` and `group show`. Backend-to-backend credential transfer still uses the global database only. (`rustconn-core/src/models/connection.rs`, `rustconn-core/src/models/group.rs`, `rustconn-core/src/secret/resolver.rs`, `rustconn-core/src/sync/full_export.rs`, `rustconn/src/state/mod.rs`, `rustconn/src/state/sync.rs`, `rustconn/src/vault_ops.rs`, `rustconn/src/dialogs/connection/`, `rustconn/src/dialogs/widgets.rs`, `rustconn/src/window/edit_group.rs`, `rustconn/src/window/connection_dialogs.rs`, `rustconn/src/window/rdp_vnc.rs`, `rustconn-cli/src/`, `po/`, `docs/USER_GUIDE.md`, `docs/CLI_REFERENCE.md`)

### Fixed
- **Embedded RDP on macOS sent the wrong keys (issue #412)** — on the macOS GTK Quartz backend the GDK hardware keycode is an Apple virtual keycode (`NSEvent.keyCode`), not an evdev keycode, but the embedded (IronRDP) client ran it through the Linux evdev→AT scancode table. Every key landed on a neighbouring one: on a German layout `qwertz` arrived as `345687`, `123` as `90ß`, and Backspace as `#`, because e.g. Apple keycode 12 (`q`) is evdev 12 (`3`). A new `macos_keycode_to_scancode` table maps the stable Apple virtual keycode straight to the IBM PC AT (Set 1) scancode the RDP server expects — letters, digits, punctuation, modifiers (Command → Super/Win), the function row (F1–F19), the navigation cluster (Help → Insert) and the numeric keypad (including Keypad `=`), with the `E0` prefix on extended keys. `send_ironrdp_key` now selects the evdev table on Linux/BSD and the Apple table on macOS at compile time; the external FreeRDP client, which was never affected, is unchanged. (`rustconn-core/src/rdp_client/input.rs`, `rustconn/src/embedded_rdp/input.rs`)

- **The tray icon now shows the real number of open sessions, and a failed connection no longer logs a false "Failed to terminate session" warning** — both read the core `SessionManager`, which the GUI never registers a terminal session in, so the tray always said 0 and every connection that failed with its tab still open logged `WARN Failed to terminate session: Session not found`. The tray now uses the same count as the quit confirmation (tabs, detached windows and external viewers), the always-failing terminate calls are gone, and the Session Manager dialog shows one "active session(s)" count instead of a second "tracked" figure that was always 0. Opening the RDP editor without FreeRDP installed (normal on macOS, where the embedded client needs none) is now logged at `info` instead of `warn`; a launch that needs FreeRDP still reports it. (`rustconn/src/app.rs`, `rustconn/src/state/sessions.rs`, `rustconn/src/window/session_lifecycle.rs`, `rustconn/src/window/sessions.rs`, `rustconn/src/embedded_rdp/detect.rs`)

- **Closing one of two sessions of the same connection no longer clears its "connected" mark in the sidebar** — the sidebar counted open sessions per connection, and one session ending is reported by several paths (the close-tab action, the notebook's page-closed hook, the terminal's child-exit handler, an embedded client's Disconnected state). Each report took one off the counter, so closing one tab of a connection with two open sessions dropped it to zero and cleared the check mark, and a failure on one session could mark a connection failed while another was still connected. The sidebar now keeps the set of open session ids per connection, so a session is removed once however many paths report it, and a reconnect in the same tab is not counted twice. External viewer sessions pass their session id to the sidebar for the same reason. (`rustconn/src/sidebar/mod.rs`, `rustconn/src/sidebar_types.rs`, `rustconn/src/external_session.rs`, `rustconn/src/window/`)
- **"System keyring" can be chosen for a saved master password on macOS** — the Secrets tab gated the keyring choice on the Linux `secret-tool` binary, which macOS never has, so picking "System keyring" to store the KeePass, Bitwarden, 1Password, Passbolt or portable-file secret was reverted and every opening of Settings logged `WARN secret-tool not found`. On macOS the choice is now gated on the Keychain probe the backend itself uses. (`rustconn/src/dialogs/settings/secrets_tab/detection.rs`)
- **Logs name the KeePass database a lookup used** — the debug line for a KeePass credential lookup now carries the `.kdbx` path, so a per-connection or per-group database (issue #411) can be told apart from the global one, and `rustconn-cli secret get/set/delete` include the path in KeePass errors. The credential-resolve timing line is now `op="connect.resolve"` instead of `ssh.connect.resolve`, because RDP, VNC and the other protocols resolve through the same code. (`rustconn/src/state/mod.rs`, `rustconn-cli/src/commands/secret.rs`, `rustconn-core/src/tracing/perf.rs`, `docs/ARCHITECTURE.md`)

### Changed
- **Code scanning moved to an in-repo CodeQL configuration** — the repository's CodeQL scan is now defined by a committed workflow (`.github/workflows/codeql.yml`) and config (`.github/codeql/codeql-config.yml`) instead of GitHub's UI-only default setup, so its scope is reviewable in a PR. The language set (actions, python, ruby, rust) and the default query suite are unchanged; the workflow uses `github/codeql-action@v4` (v3 is deprecated in December 2026) and a per-language job-level concurrency group, and `paths-ignore` keeps non-product trees (Rust integration tests and benchmarks, packaging and developer tooling, build output) out of the scan. Thirteen pre-existing high/critical alerts were reviewed and dismissed as false positives: each flagged a `#[cfg(test)]` fixture — a hard-coded test passphrase or a synthetic certificate-mismatch message — not a production secret or log. (`.github/workflows/codeql.yml`, `.github/codeql/codeql-config.yml`)

### Dependencies
- **Updated** (semver-compatible): arc-swap 1.9.3→1.9.4, cc 1.11.0→1.11.1, flate2 1.1.10→1.1.11, inout 0.2.5→0.2.6, libz-sys 1.1.31→1.1.32, lzma-rust2 0.24.0→0.25.0, serde_spanned 1.1.2→1.1.3, smallvec 1.16.4→1.16.5, toml 1.2.0→1.2.1, toml_datetime 1.1.2→1.1.3, toml_edit 0.25.18→0.25.19, uuid 1.29.0→1.29.1, zip 9.4.0→9.4.2. `cargo deny check advisories` is clean; `cargo-sources.json` regenerated for the Flatpak/Flathub manifests. Bundled Flatpak FreeRDP (3.33.0) and cJSON (1.7.19) are at their latest releases, every pinned CLI download (TigerVNC 1.16.2) is current, and `ironrdp-rdpdr` 0.9.0 is still the latest release, so the 0.24.7 known issue about embedded RDP shared-folder names still applies.

## [0.24.7] - 2026-11-06

### Added
- **The Kubernetes connection editor can pick a context from the kubeconfig** — the Context field keeps its free-text entry but gains a button that lists the contexts defined in the kubeconfig the connection names (or `$KUBECONFIG` / `~/.kube/config` when the field is empty), with the current-context marked. The list is read with `serde_yaml`, taking only the context names and `current-context` and ignoring every other kubeconfig field; a missing or unreadable file simply offers nothing to pick. (`rustconn-core/src/protocol/kubernetes.rs`, `rustconn-core/src/protocol/mod.rs`, `rustconn/src/dialogs/connection/kubernetes.rs`)
- **A crash from a Rust panic is now recorded to a local log, and the next launch says so** — a panic writes its message, location, backtrace and the build version to `$XDG_STATE_HOME/rustconn/crash-<timestamp>.log` (the OS data directory where there is no state directory). The next start shows a banner with an **Open Log** button; once the log has opened the logs are cleared so a handled crash does not reappear (if it cannot be opened, the banner stays and a toast names the file). A panic the program survives (one caught internally, or one that only ends a background thread) is removed again on a clean exit, so the banner appears only when the previous run really did not finish. The log is owner-readable only, stays on the machine and is never sent anywhere — review it before sharing, as a panic message can contain formatted data. This catches Rust panics only; a `SIGSEGV` inside a C library (GTK, VTE) does not come through here. (`rustconn-core/src/crash_report.rs`, `rustconn/src/main.rs`, `rustconn/src/app.rs`, `rustconn/src/window/mod.rs`)
- **Run a saved snippet from the Command Palette, and save a terminal selection as a snippet** — the palette's new `!` prefix lists snippets and runs the chosen one; because the palette hangs off the main window, it always asks for confirmation first, so a snippet is never sent to the wrong terminal when a detached window or split pane holds focus (issue #315). The terminal right-click menu gains **Save Selection as Snippet…**, which opens the snippet editor with the selection of the terminal you right-clicked pre-filled (also in a split pane or a detached window) for you to name and trim — nothing is stored without your action. (`rustconn-core/src/search/command_palette.rs`, `rustconn/src/dialogs/command_palette.rs`, `rustconn/src/dialogs/snippet.rs`, `rustconn/src/terminal/config.rs`, `rustconn/src/window/snippets.rs`, `rustconn/src/window/snippet_actions.rs`)

### Fixed
- **A "Save N Files" RDP download no longer hangs on "Downloading…" when the clipboard channel is gone, and a failed save is now shown as a toast (issue #390)** — if the CLIPRDR channel was unavailable when a file-contents request was made, the request returned silently and the button sat on "Downloading…" forever, because the error was raised through the clipboard backend that no longer existed. The failure is now reported straight through the session event channel, so the batch unwinds. A batch that could not save every file also raises an error toast, not just a 3-second inline status the user could miss. (`rustconn-core/src/rdp_client/client/commands.rs`, `rustconn/src/embedded_rdp/polling_handlers.rs`)
- **Embedded RDP now locks the remote file clipboard during a copy, so a file copied in the session survives a focus change (issue #390, Fix B)** — the embedded clipboard channel now advertises `CAN_LOCK_CLIPDATA`. When the server also supports it (Windows does), IronRDP sends a Lock PDU after the Format List Response whenever the server announces a file list, carries the `clipDataId` on each File Contents Request, and expires each lock on its own. Without it a server was free to drop the File Stream data the moment its clipboard changed — the "copy a file in the session, switch to another app, come back and Save" race that the earlier Fix A could not cover, because the focus-return format announce replaced the clipboard before the download even began. (`rustconn-core/src/rdp_client/clipboard.rs`)
- **A minimal RDP server that rejects the external client now says which client to use (issue #409)** — against a screen-sharing server that implements only the rdpgfx/AVC (EGFX) capability set, such as KRDP, the external FreeRDP client advertises the full standard RDP capabilities in Demand Active and the server tears the session down during the capabilities exchange (`CAPABILITIES_EXCHANGE` / `STATE_RUN_FAILED`). That failure used to surface as a bare `RDP connection failed (exit status …)`. It now reports that the server only speaks the embedded client's protocol and tells the user to set the connection's Client Mode to Embedded, which negotiates only the EGFX caps and connects to the same server. (`rustconn/src/embedded_rdp/connection.rs`, `po/`)

### Changed
- **Importing connections with passwords no longer freezes the window** — storing the imported credentials in the chosen secret backend now runs on a background task with a toast when it starts and another reporting how many were stored, instead of blocking the UI for the whole batch. The connections and groups still appear at once; only the credential storage, which is several seconds per credential for a CLI-backed backend such as Bitwarden, moves off the main thread. (An earlier fix had already stopped these passwords going to the system keyring regardless of backend; this removes the remaining freeze, W4/FC §6a.) (`rustconn/src/state/sync.rs`, `rustconn/src/window/connection_dialogs.rs`, `po/`)
- **Opening the Passbolt vault and the export output folder now goes through the desktop portal** — both used to spawn `xdg-open` (or `open` on macOS); they now use `gtk4::UriLauncher` / `gtk4::FileLauncher`, so they let the desktop choose the handler and work inside the Flatpak sandbox. The external file manager for an `sftp://` browse is deliberately left spawning directly, because it must inherit RustConn's ssh-agent socket, which a portal launch would not pass on. The now-unused `open` crate dependency is dropped. (`rustconn/src/dialogs/settings/secrets_tab/mod.rs`, `rustconn/src/dialogs/export.rs`, `rustconn/Cargo.toml`)

### Dependencies
- **Updated** (semver-compatible): zip 9.3.0→9.4.0. Dropped with the `open` crate: open 5.4.5, is-docker 0.2.0, is-wsl 0.4.0. `cargo deny check advisories` is clean; `cargo-sources.json` regenerated for the Flatpak/Flathub manifests. Bundled Flatpak FreeRDP (3.33.0) and cJSON (1.7.19) are at their latest releases, and TigerVNC, the only pinned CLI download, is current at 1.16.2.

### Known Issues

- **Embedded RDP shared folders show only the first letter of their name, and a folder with a non-ASCII name (e.g. Cyrillic) is refused** — since 0.24.3 the embedded client uses `ironrdp-rdpdr` 0.9, which announces the share name as UTF-16 as MS-RDPEFS asks, but Windows reads it as 8-bit characters. A share named `Downloads` therefore appears as `\\tsclient\D` (reported upstream for Windows 11 and Server 2022/2025), and one named `Загрузки` is refused by Server 2019 and 2025 with `STATUS_UNSUCCESSFUL` (the session continues and a toast names the folder, issue [#407](https://github.com/totoshko88/RustConn/issues/407)). The external FreeRDP client is not affected and shows both names correctly, so set the connection's Client Mode to External if you need the share name. The ASCII case is fixed upstream in [IronRDP#2342](https://github.com/Devolutions/IronRDP/pull/2342) (not yet released), and a fix for non-ASCII names is proposed in [IronRDP#2383](https://github.com/Devolutions/IronRDP/pull/2383) ([IronRDP#2382](https://github.com/Devolutions/IronRDP/issues/2382)); RustConn picks them up with the next `ironrdp-rdpdr` release that carries them.

## [0.24.6] - 2026-11-05

### Added
- **SSH keys RustConn adds to the agent itself expire after 12 hours and are removed on exit** — when a multi-hop `ProxyJump` connect or an SFTP / Midnight Commander launch needs a key the agent lacks, RustConn runs `ssh-add -t 43200` without prompting (30-second limit), records the key (and its certificate), and removes exactly those keys on exit over the agent socket. Keys already in the agent before RustConn's add, or added in Settings → SSH Agent, are never touched; a key you re-add with `ssh-add` in a terminal after RustConn added it is still removed on lock, suspend or exit. Legacy PEM/PKCS#8 keys are added only to an empty agent and rely on the 12-hour lifetime, as do keys added by `rustconn-cli sftp` when it cannot clean up. (`rustconn-core/src/ssh_agent/own_keys.rs`, `rustconn-core/src/ssh_agent/wire.rs`, `rustconn-core/src/ssh_agent/keyfile.rs`, `rustconn-core/src/sftp.rs`, `rustconn/src/window/protocols_ssh.rs`, `rustconn/src/app.rs`, `rustconn-cli/src/commands/sftp.rs`, `docs/USER_GUIDE.md`, and others)
- **The same keys are also removed on screen lock and suspend (Linux)** — a new D-Bus listener (`lock_events`, non-default `lock-events` feature, always on in the GUI) watches login1 `PrepareForSleep` and the freedesktop/GNOME screensaver `ActiveChanged`, holding a sleep delay inhibitor so the removal finishes before suspend. Unreachable sources are logged and skipped. Flatpak and Snap get no new permissions: in the Flatpak lock/suspend removal is an opt-in `flatpak override` (`docs/INSTALL.md`); in the Snap screen lock works, suspend is not detected. (`rustconn-core/src/lock_events/`, `rustconn-core/Cargo.toml`, `rustconn/src/app.rs`, `docs/INSTALL.md`, `docs/SNAP.md`, `docs/USER_GUIDE.md`, and others)
- **The same keys are also removed on screen lock and sleep (macOS)** — a new isolated FFI crate, `rustconn-lock-sys`, observes `com.apple.screenIsLocked` and `NSWorkspaceWillSleepNotification` and feeds them into the same `lock_events` subscribers through `lock_events::notify`. Sleep is not delayed for the removal; an unfinished removal completes on wake. (`rustconn-lock-sys/`, `rustconn-core/src/lock_events/mod.rs`, `rustconn/src/app.rs`, `.github/workflows/ci.yml`, `scripts/verify.sh`, `docs/ARCHITECTURE.md`, and others)
- **Encrypted SSH keys are unlocked once per session in RustConn's own dialog** — a connect, reconnect, first jump host, or SFTP / mc launch with a passphrase-protected OpenSSH key the agent lacks now opens an **Unlock SSH Key** dialog (three attempts); the key goes into the agent for 12 hours and is removed on exit, lock and suspend like the other keys RustConn adds. The passphrase is never stored or read from a vault. Cancel, a refusing agent (e.g. 1Password) or a held certificate fall back to `ssh`'s own terminal prompt; a Cancel is remembered for that key and agent socket until RustConn quits, and legacy PEM/PKCS#8 keys or an agent that does not answer get no dialog. Concurrent connects share one dialog, and the SSH editor warns that Agent Forwarding exposes unlocked keys. - **Embedded RDP showed evenly spaced horizontal stripes across the desktop (#389)** — IronRDP reports each framebuffer damage region as an `InclusiveRectangle`, so the pixel at its `right`/`bottom` edge is part of the region, but the session loop sized the rectangle with a plain subtraction (`right - left`, `bottom - top`), which is one short on each axis. Every update therefore left its last row and last column unpainted. The region is now converted with `+ 1` on width and height, and the existing clamp keeps the last band from reading past the framebuffer. ### Fixed
- **Embedded RDP and VNC sessions timed out on hosts with an unreachable IPv6 address** — the embedded clients connected with `TcpStream::connect("host:port")`, which tries the resolved addresses one after another. When a name resolves to both an AAAA and an A record and the IPv6 address never answers, as on a VPN that hands out IPv6 addresses it does not route, the first attempt used up the whole connect timeout and the session failed with `Operation timed out` without ever trying the IPv4 address that works. Connecting now races the addresses (RFC 8305, "Happy Eyeballs"): families alternate, each attempt gets a 250 ms head start, and a refused address hands over at once, so such a host connects over IPv4 in about a quarter of a second. The same dialler is used by the embedded RDP and VNC clients, by a broker's redirect to its session host, by *Check if online*, and by *Test Connection*. The MPTCP setting now also applies to direct embedded RDP connections in builds with RD Gateway support, which used plain TCP regardless. Connections through an RD Gateway are dialled by `ironrdp-mstsgu` and are unchanged. (`rustconn-core/src/connection/dial.rs`, `rustconn-core/src/rdp_client/client/connection.rs`, `rustconn-core/src/vnc_client/client.rs`, `rustconn-core/src/host_check.rs`, `rustconn-core/src/testing/mod.rs`)
- **Embedded RDP sessions played no sound unless a folder or printer was shared** — with audio set to *Play on this computer* and nothing shared, the embedded client joined the sound channel (RDPSND) without the device redirection channel (RDPDR). A Windows host starts sound only once RDPDR is joined too, so the server never sent a format list or a single sample, and nothing reported a problem. FreeRDP registers RDPDR whenever sound is on for the same reason; the embedded client now does as well. (`rustconn-core/src/rdp_client/client/connection.rs`)
- **The Quality performance mode no longer offers the server a lossy codec** — Quality asked for lossless bitmaps but also advertised the RemoteFX codec, which is lossy and which a server prefers when it is offered, so the request for lossless output was undone. That is what an embedded session shows whenever the server does not open the GFX pipeline, as some Windows hosts and policies never do, and text arrived soft and smeared. Quality now offers no codec, so the server sends lossless 32-bit bitmaps, which take noticeably more bandwidth; Balanced still offers RemoteFX for links where that matters, and Speed is unchanged. (`rustconn-core/src/rdp_client/client/connection.rs`)
- **Embedded RDP text was uneven on fractional-scaling displays** — with Display Scale *Auto* the remote desktop is requested at the widget's logical size and stretched to the display, and on a 125% or 150% display that stretch used Nearest filtering, which repeats every fourth or every second row and column, so strokes came out with uneven widths. The framebuffer is now drawn with Nearest only when each remote pixel lands on a whole number of device pixels (Native, or Auto at 100% or 200%), and with bilinear filtering otherwise. For pixel-exact text on a fractional display, Display Scale *Native (full HiDPI)* still avoids the stretch altogether. (`rustconn/src/embedded_rdp/drawing.rs`)
- **`.rdp` files saved by Remote Desktop Connection could not be imported or opened** — `mstsc` saves `.rdp` files as UTF-16LE with a byte-order mark, and the importer read them as UTF-8, so importing one, or double-clicking it, failed with an invalid-UTF-8 error. A UTF-8 file with a byte-order mark lost its first key the same way, which refused the file outright when that key was `full address`. The byte-order mark now decides the encoding (UTF-16LE, UTF-16BE or UTF-8), and a file without one is read as UTF-8. (`rustconn-core/src/import/rdp_file.rs`)
- **Touchpad smooth scroll and high-velocity mouse wheel no longer panic in RDP sessions** — kinetic scrolling and high-resolution wheel events can emit large deltas that exceed RDP's 9-bit two's-complement limit `[-256, 255]`. Large deltas are now chunked into safe increments of at most 120 (standard Windows `WHEEL_DELTA`), and horizontal/touchpad scrolling is scaled smoothly, preventing connection drops from `ironrdp-pdu` panics. (`rustconn-core/src/rdp_client/client/commands.rs`, `rustconn/src/embedded_rdp/input.rs`)

## [0.24.0] - 2026-10-28

### Fixed
- **Switching the preferred secret backend drops the old backend's unlock state (W1)** — rebuilding the secret-manager chain on a settings save cleared the per-connection credential cache but left Bitwarden's process-global unlock marks (the session key, the verify timestamp, the last-sync timestamp) and the global-secret cache in place. After switching the preferred backend away from Bitwarden, a stale session key kept answering the fast path and a global secret resolved from the old backend could be served for up to its cache TTL. The switch now clears the Bitwarden session state and the global-secret cache — but only when the preferred backend actually changes, so flipping an unrelated read-only or root-search toggle still keeps an unlocked session (no re-lock, no speed regression). (`rustconn-core/src/secret/bitwarden.rs`, `rustconn/src/state/mod.rs`)
- **Tunnel askpass helper script is created atomically with 0700 (W4, review SEC-4)** — `write_askpass_script` created the helper with `File::create` and only chmodded it to 0700 afterwards, so for a brief window it existed world-readable and a symlink planted at its (random) path could have redirected the write. It now opens the file with `create_new` (O_EXCL) and mode 0700 set at open time, matching the tunnel secret file. The script holds no secret (only the name of the env var to read); this is defence-in-depth. (`rustconn-core/src/ssh_tunnel.rs`)
- **A mouse selection in a terminal no longer disappears while it is being dragged when the remote side redraws on a timer (contributed by Christian Petri, @Cyb0rk)** — with byobu (or any tmux status bar with a clock) on the remote host, the selection was dropped every second, so selecting more than a few characters was nearly impossible. VTE deselects when output arrives before the drag ends, and protects its own PTY by not reading from it during a drag. RustConn owns the PTY and feeds VTE directly, which bypassed that pause. The output loop now waits while the primary button is down and VTE has a selection, and resumes on release or when the terminal loses focus. Nothing is dropped: the relay's bounded queue fills and the child is held back, as with VTE's own PTY. A click that goes to a mouse-tracking application (tmux with mouse on, vim) creates no selection and does not pause output. Closing the tab in the middle of a drag no longer leaves the output loop waiting for a release that never comes, and closing the tab or reconnecting in the middle of a drag no longer stalls the window while the session's PTY threads are stopped. (`rustconn/src/terminal/selection_hold.rs`, `rustconn/src/terminal/pty_relay.rs`, `rustconn/src/terminal/mod.rs`)
- **The current prompt line is no longer held back on prompts that use `❯` and similar glyphs** — on a host with an oh-my-bash `powerline-multiline` prompt the last line (`❯ ` and the cursor) did not appear in a tab until more output arrived, although a separate terminal showed it at once. Since 0.23.6 the OSC 52 filter that sits in front of VTE treated a bare `0x9d` byte as the 8-bit OSC introducer, but in UTF-8 that is a continuation byte inside ordinary characters (`❯` is `e2 9d af`, as are box-drawing characters such as `╝` and many Nerd Font glyphs), so the rest of the line was buffered as an OSC string; it happened with the OSC 52 setting off too. The filter now follows VTE, which decodes UTF-8 before parsing: the 8-bit controls are recognised only as the encoded code points `c2 9d` and `c2 9c`, and `CAN`/`SUB` and the other C1 controls abandon an open string. What VTE is fed is equivalent to the stream it would have read: the same text and controls, the same OSC strings, minus the OSC 52 offers the filter takes. Each sequence the filter removes (an offer, a query, an over-long string, or an OSC string left open when the session ends) is replaced by a single `CAN`, which VTE ignores on screen and which ends whatever the filter let through just before it, so a lone `ESC`, a UTF-8 lead byte or an abandoned OSC string cannot pair with the bytes that follow the gap, and a removed offer can no longer turn the text after it into an OSC 52 that VTE would act on. Offers VTE would also read as OSC 52 are no longer missed when control characters it ignores sit inside the string or between `ESC` and `]`, and an OSC string still open when the session ends is no longer handed to VTE, where the next `BEL` shown in the tab could complete it. Only a genuinely incomplete escape or a lone `c2` is held at the end of a read. (`rustconn/src/terminal/osc52.rs`)

- **The browser SOCKS tunnel listens on loopback only, whatever `GatewayPorts` says** — the tunnel was started with `-D <port>` and no bind address, so a `GatewayPorts yes` in the user's `~/.ssh/config` made the SOCKS proxy listen on every network interface and anyone on the local network could route traffic through the user's SSH or Tailscale host without authenticating. It is now `-D 127.0.0.1:<port>` for both OpenSSH and Tailscale SSH, the same address the readiness probe and the browsers already use. (`rustconn-core/src/ssh_tunnel.rs`)
- **"Open Browser via Tunnel" ignores repeat clicks while its tunnel starts** — the action raises the tunnel in the background (up to 10 seconds) with no sign that anything was happening, so a second click started a second tunnel and a second browser. It now shows a "Starting the tunnel…" toast on the click and ignores further clicks for the same connection until the tunnel is up or has failed. The in-flight mark is cleared on success, on failure and when the worker dies, and other connections are not affected. Quitting while the tunnel starts still leaves its `ssh -N` running (unchanged, deferred). (`rustconn/src/window/edit_actions.rs`)
- **Jump-host tunnels for RDP, VNC and SPICE listen on loopback only (security)** — the tunnel was started with `-L <port>:<host>:<port>` and no bind address, so `GatewayPorts yes` in the user's `~/.ssh/config` made the forwarded port listen on every network interface and anyone on the local network could reach the RDP/VNC/SPICE target through it. It is now `-L 127.0.0.1:<port>:<host>:<port>` for both OpenSSH and Tailscale SSH, built by the same helper as the SOCKS bind; every consumer already connects to `127.0.0.1`. (`rustconn-core/src/ssh_tunnel.rs`, `rustconn-core/src/models/protocol.rs`, `docs/USER_GUIDE.md`)
- **"Open Browser via Tunnel" is offered only where it can work (issue #397 follow-up)** — the sidebar decided whether to show the item from a Zero Trust connection's `provider`, while the code that starts the tunnel checked its `provider_config`, so an imported or hand-edited connection whose two disagreed showed the item and then did nothing. (`rustconn-core/src/ssh_tunnel.rs`, `rustconn/src/sidebar/view.rs`, `rustconn/src/window/edit_actions.rs`)
- **The CPU/RAM monitoring bar no longer stays washed out after Reconnect (issue #398)** — when an SSH session dropped, the monitoring collector stopped after three consecutive execution errors and dimmed the bar (the `monitoring-stale` style, 50% opacity) with a warning icon to mark its metrics as stale. Reconnect then skipped starting monitoring, because its guard treated any bar already in the session map as live, so the dimmed bar stayed in place and its metrics never updated again — including the race where Reconnect was pressed before the collector had even noticed the drop. Reconnect now explicitly discards the previous connection's bar and collector before reconnecting, and starting monitoring replaces a bar whose collector has already stopped instead of skipping it, so the bar comes back exactly as on a first connect: one bar, no stale class, no warning icon. - **Embedded RDP hands a session that stalls after TLS to the external client (issue #392)** — against GNOME Remote Desktop's Remote Login mode, IronRDP completed the TLS upgrade and the TOFU certificate check, then waited the full handshake budget (60s+) inside `connect_finalize` (NLA → MCS → licensing → capabilities) with no error. ### Changed
- **Listing ssh-agent identities no longer spawns a process (W1 A1)** — reading the keys an agent holds ran `ssh-add -l` and, for the public-key path, a `ssh-keygen` per key, so a connect that consulted the agent cost one process plus one per identity on the way in. RustConn now speaks the ssh-agent protocol directly over `SSH_AUTH_SOCK` (`SSH_AGENTC_REQUEST_IDENTITIES`) in one round trip and computes each key's SHA256 fingerprint in-process with `ring` — no process, under a millisecond. The old `ssh-add -l` path remains as a fallback for an agent the native client cannot talk to, so behaviour is never worse than before. Adding and removing keys still go through `ssh-add` for now. (`rustconn-core/src/ssh_agent/wire.rs`, `rustconn-core/src/ssh_agent/mod.rs`)
- **One `ssh-add` path for the whole app (W1 A3)** — loading a connection's SSH key into the agent before an mc/file-manager launch was five near-identical `ssh-add` spawns (four in the GUI, one in core), each re-deriving the same stdin/stderr wiring and Flatpak `SSH_ASKPASS` strip, so a fix to one could miss the others. They now call a single `rustconn_core::sftp::ensure_identity_loaded`, which returns the agent's stderr on failure so each caller keeps only its own result handling (a toast, a sidebar status, a log line). No behaviour change: a missing or absent key still proceeds without blocking the launch. (`rustconn-core/src/sftp.rs`, `rustconn/src/window/edit_actions.rs`)
- **Secret global variables are read from the vault once per session window, not once per connect phase (W1 P1)** — a connection that substitutes a secret global variable re-read it from the vault every time, and a single SSH connect reads the globals two to three times (the ASK scan, the launch substitution, the reconnect path), each a blocking vault lookup. Resolved secret globals are now held in a 300-second session cache (the same window as the per-connection credential cache), so the repeated reads of one connect and a quick reconnect cost nothing; a vault miss is not cached, and saving the variables clears the cache so an edited secret is never served stale. (`rustconn/src/vault_ops.rs`, `rustconn/src/window/history_actions.rs`)
- **`ssh -G` no longer spawns on the GTK main thread during SSH connect (W1 P3)** — deciding whether OpenSSH's own config routes a host through a proxy (which gates whether the target password may be delivered by askpass) ran `ssh -G` synchronously inside the connect-args build on the UI thread. On the initial connect it now runs in the same background phase as the port check and the answer is handed to the build, so the main thread spawns no process. The reconnect path and a connect with the port check disabled still compute it synchronously as a fallback. No behaviour change: a config that routes through a proxy still blocks target-password askpass, keeping the credential off the bastion. (`rustconn/src/window/protocols_ssh.rs`)
- **FreeRDP version detection is warmed in the background at startup (W4)** — the first RDP connect of a session probed each candidate FreeRDP client (`… --version`) synchronously on the GTK main thread to pick and configure the right binary — up to seven short spawns the user waited through while the window was already up (one connect in the field showed five). A fire-and-forget background thread at startup now fills the same process-wide version cache the connect path reads (by the same keys, local `PATH` and the Flatpak host's `host:` form), so by the time a connection opens the lookups are cache hits and the main thread spawns nothing. It changes no detection logic and caches nothing a probe would not: a client missing, slow or without a parseable banner at warm-up time is simply re-probed on first use, so behaviour is never worse than before. (`rustconn/src/embedded_rdp/detect.rs`, `rustconn/src/app.rs`)
- **Loading an SSH key into the agent skips `ssh-add` when the key is already there (W3 A3)** — the single `ensure_identity_loaded` path added in W1 always spawned `ssh-add`, even before an mc or SFTP launch on a key already loaded at connect time, where the add is a no-op that still costs a process. It now reads the key's public fingerprint without a passphrase (A2, the public half of an OpenSSH key is in the clear even when encrypted; a sibling `.pub` is the fallback) and compares it against the agent's identities over the native wire protocol (A1, one Unix-socket round trip, no process). An already-loaded key returns immediately with zero spawns. The agent query is bounded by a 3-second timeout so a broken or launchd-throttled agent cannot hang a main-thread caller, and any uncertainty (no fingerprint, no agent, a timeout) falls through to the existing `ssh-add` path — so behaviour is never worse than before and an encrypted key not yet loaded still goes through `ssh-add`. (`rustconn-core/src/sftp.rs`)
- **A live ControlMaster socket skips the pre-connect port check (W1 P4)** — when a master connection to the host is already open, a new SSH session multiplexes over it, so the TCP connection is already up and the pre-connect port check is redundant. RustConn now detects an existing ControlMaster socket for the host and port (a real Unix socket sharing the `ControlPath` prefix, not a stale regular file) and skips the port check, saving a round trip. It does not run `ssh -O check` — that would spawn the process the fast path exists to avoid — and a socket that is present but dead is simply re-established by OpenSSH's `ControlMaster=auto`, so the only cost of a rare false positive is a skipped port check that proxy/bypass connections already skip safely. (`rustconn-core/src/monitoring/ssh_exec.rs`, `rustconn/src/window/protocols_ssh.rs`)
- **Multi-bastion hop-password resolution extracted into one tested function (W1 P2a)** — the per-hop password logic for a jump-host chain (issue #203) was inline in the connect-args build, interleaved with the chain walk. It now lives in `assemble_hop_passwords`, which keeps the first reference hop's already-resolved password in place, resolves each deeper hop through an injected resolver (cache then vault, warming the cache), and keeps the result index-aligned with the jump-host list so a string-proxy gap or an unresolvable hop never shifts the others. The vault read is still synchronous — this is the extraction and dedup step; moving it off the main thread is a separate change. (`rustconn/src/window/protocols_ssh.rs`)

- **Bitwarden unlock no longer blocks on `bw sync` (W1)** — unlocking the vault ran `bw sync` synchronously before handing back a ready backend, and on a snap/Flatpak `bw` that one call cost around six seconds on the critical path to a usable vault at startup (issue #353 trace: `bw status` + `bw unlock` + `bw sync` back to back, ~15 s total). A sync that ran within the last ten minutes is not repeated, so reconnects and batch lookups keep skipping the round trip. The background and first-retrieve syncs are serialized process-wide, so a connect made the instant the background sync starts waits for it rather than firing a second `bw sync` beside it. (`rustconn-core/src/secret/bitwarden.rs`, `rustconn/src/app.rs`)
- **SSH askpass helper moved from the GUI into `rustconn-core` (W3 K1)** — the prompt-aware `SSH_ASKPASS` helper that releases a stored target or bastion password only for an account-password prompt (and stays silent for key passphrases, host-key questions, OTP and password-change prompts), its per-hop script cache, the owner-only secret files and the per-child askpass environment lived in `rustconn/src/window/protocols_ssh.rs`, out of reach of the core consumers that need them next (key setup, the CLI, monitoring). - **Bitwarden no longer unlocks twice when a connect starts during the startup unlock (issue #353)** — the startup unlock runs on its own thread, outside the vault-op lock. Every step appeared twice in the reporter's logs, and each `bw` call takes seconds. `auto_unlock` now runs one caller at a time, so the second one waits; if the first stored a session, the second takes the fast path, otherwise it repeats the checks on its own. ## [0.23.9] - 2026-10-11

### Fixed
- **RDP now connects to KRdp / NLA-less Linux hosts that reject the embedded client's CredSSP (#366)** — a KRdp 6.6.x server built on FreeRDP 3.32.x advertises `HYBRID_EX` ("Ext") security it cannot actually complete: the embedded IronRDP client lets the server pick `HYBRID_EX`, the server's NTLM/SAM path fails internally, and the client sees `STATUS_LOGON_FAILURE` (`0xc000006d`) even with correct credentials — byte-for-byte identical to a wrong password, which is why #366 was reported as "invalid username or password". This is a server-side regression (FreeRDP issue [#13567](https://github.com/FreeRDP/FreeRDP/issues/13567); KRdp fixed it in 6.7.90). Remmina reaches the same server because it negotiates **plain TLS**, which never offers `HYBRID_EX` — confirmed live, with `/sec:tls` the FreeRDP negotiation drops to `nego_enable_ext: FALSE`. RustConn now does the same: on that rejection it hands the session once to external FreeRDP with the security layer pinned to TLS (`/sec:tls`), matching Remmina. The decision is a pure, unit-tested `warrants_tls_only_fallback` in `rustconn-core::rdp_client::failure` — it fires only for the ambiguous `InvalidToken`/logon-failure shape (never for account-state statuses TLS cannot fix) and only once, so if the TLS-only path is rejected too the real error surfaces with actionable advice (update KRdp to 6.7.90+, set `ExtSecurity=0`, or pin FreeRDP 3.31.0) instead of looping. Two further tweaks were needed for KRdp, both bisected live against a real server: the explicit colour depth is dropped (an explicit `/bpp:32` made KRdp answer the capabilities exchange with `PDU_TYPE_DEACTIVATE_ALL`; `None` lets FreeRDP negotiate it), and the external window opens resizable with content scaling (`/smart-sizing` + a 1280×800 start size) instead of the fixed monitor-sized `/size:100%`. - **An RDP tab no longer hangs on "Starting RDP…" / "running in external window" after the external client closes (#366)** — two bugs kept the tab stuck once the external FreeRDP window ended: `notify_ironrdp_state` changed the state but never repainted the placeholder (so the Cairo surface kept the previous label), and the external-exit watchdog both stopped polling after 30s and stood down silently on a post-window exit instead of moving the GUI to Disconnected. - **The embedded Wayland FreeRDP fallback now honours the security layer and NLA switches** — the embedded `wlfreerdp3` subsurface path built its argument vector by hand and omitted `/sec` entirely, so it always ran FreeRDP's own default (Negotiate → NLA) regardless of the connection's **Security layer** or **Disable NLA** settings. ## [0.23.6] - 2026-10-09

### Added
- **OSC 52: a remote yank can reach the local clipboard (opt-in)** — VTE parses `OSC 52 ; c ; <base64>` and then drops it: through 0.84 its `XTERM_SET_XSELECTION` handler is a no-op, so a yank in a remote Neovim — or in tmux with `set-clipboard external` — put the text nowhere. GNOME Terminal and xfce4-terminal inherit the same hole, so this was a missing capability rather than a RustConn bug, and RustConn needs its own because VTE has no API to switch the handler on. A new `terminal::osc52::Osc52Filter` sits on the session output path (`TerminalNotebook::deliver_output_to`), lifts the offers out of the PTY stream before `Terminal::feed` sees them, and writes them through the same `display().clipboard().set_text()` call copy-on-select uses. It is a byte filter rather than a parser for its own sake: every other byte is passed through in order — `OSC 0` titles, `OSC 133` shell-integration marks, plain `ESC` sequences — and a string the stream ends inside is handed back by `finish()` instead of being kept, because an unterminated OSC left in the stream would make VTE swallow the rest of the session as body. A sequence can straddle PTY reads (8 KiB `READ_CHUNK`), so the filter keeps state between chunks; one test feeds the same offer at every possible split point and one byte at a time and requires identical output. All three terminators (`ESC \`, `BEL`, C1 `ST`) and both introducers (7-bit and C1) are recognised. **Security**: the switch is **Settings → Terminal → "Remote clipboard (OSC 52)"** and defaults to **off**, since a host that can write the clipboard can aim a pastejacking payload at the next terminal the user pastes into. Reads are never served in any configuration — an `OSC 52 ; c ; ?` query is dropped unanswered, so the local clipboard cannot be exfiltrated this way — only the `c` (CLIPBOARD) selection is honoured, with `p` (primary) and `s` (select) passed through untouched. A payload is capped at 1 MiB, is base64-decoded into a `Zeroizing` buffer so the plaintext is wiped on drop, must decode to valid UTF-8 to reach the clipboard, and the decoded text is never logged. The output filter runs before session-transcript observers too, so an enabled offer is lifted out of the saved log as well as the display; with the setting off the sequence reaches both untouched. Remote tmux needs `set-clipboard external` (and `allow-passthrough on`) to forward the sequence; a DCS-wrapped passthrough is not unwrapped yet. (PR #372, thanks @shafiev)

### Fixed
- **The high-contrast tab-bar line is neutralised on GTK < 4.22 as well** — the override that repaints the tab bar's dividing line in the window tone (so it blends into the content the way Nautilus' does) was wrapped in a `@media (prefers-contrast: more)` block, which only GTK 4.22+ parses. ## [0.23.1] - 2026-10-06

### Added
- **A Local Shell tab can be given a name of its own** — right-clicking a Local Shell tab now offers **Rename Tab…**, which titles the tab with whatever is typed (*build logs*, *tails*, *irssi*) instead of leaving every shell titled **Local Shell**. The label names the tab only: no connection is created and the shell itself is untouched. Leaving the field empty restores the default name, because an untitled tab cannot be told apart from a broken one in the tab bar. The label is remembered across restarts with Session Restore, since the snapshot already stores each tab's title and the Local Shell now reopens under it rather than under a hardcoded name; a saved workspace carries it too. The item is offered on Local Shell tabs only — a tab with a saved connection is renamed by editing that connection, which keeps the sidebar, the history and every open tab in step. In the dialog, **Enter** commits the label through the same path as **Apply**, and the field takes the keyboard focus on open.
- **A tab's group now survives Session Restore** — the restore snapshot carried each tab's title but discarded its tab group, so a grouped tab (a Local Shell or a connection) reopened ungrouped after a restart. The snapshot now records the group alongside the title and reapplies it on restore — synchronously for a Local Shell, and through the session-start observer for a connection, whose tab appears asynchronously after credential resolution. The group is carried structurally, never baked into the stored name, so a grouped tab comes back under its base label (even one that itself looks like `[x] y`) with the `[group]` prefix composed once rather than doubled, and a snapshot written by an older version (which has no group field) still loads and simply restores ungrouped. A saved workspace reapplies the group for Local Shell tabs; a connection reopened from a workspace, and a SPICE connection whose pre-connect port check defers the tab, still restore ungrouped — their start paths carry no observer yet.
- **Opt-in directional tab-close items (Settings → Interface → Window)** — the tab context menu's close block stays short by default (**Close Tab**, **Close Others**, **Close All Tabs**), and a new **Show directional tab-close items** switch adds **Close to the Left** and **Close to the Right** for the workflow that closes a run of tabs to one side. Off by default, since shown unconditionally they lengthen the menu for everyone; the toggle takes effect on the next right-click, and a config written before the key existed loads with the items hidden.

### Changed
- **The sidebar's "⋯" menu carries the connection-management actions again** — the 0.23 redesign had moved **New Connection**, **New Group**, the **Tools** managers (Clusters, Workspaces, Snippets) and **Import/Export** out of the sidebar's secondary menu into the content header's primary menu, on a one-menu-per-window reading of the HIG. In practice that put the actions a user reaches for most two clicks farther away — across to the far header and down through a submenu — so they live in the sidebar "⋯" menu again, beside the list they act on, grouped as Create · Tools · List · Select · Sort. The icon stays the three-dot `view-more` (⋯), a panel-scoped secondary menu, not a second hamburger. The content header's primary menu still lists the same entries app-wide, so nothing was lost there — this is a deliberate, convenient duplication of the list-scoped subset. **Select Connections** and the two sort orderings remain.
- **The tab context menu is lighter and its Monitor control is now self-explanatory** — the **Copy** block (Host, Port, Address, Username, Password) was removed from the tab menu: it duplicated the sidebar connection menu's tidy `Copy ▸` submenu, and copying a connection's fields is an operation on the connection object, which belongs where connections are listed rather than on the live-session tab. The tab menu now carries only session actions plus **Edit Connection…**, which stays as the one way to reach the editor from an active tab regardless of the sidebar selection. The **Monitor** control is now a **Monitor ▸** submenu of radio items — **Off**, **Activity**, **Silence**, **Command finished** — with the current mode shown selected, so a mode is chosen explicitly in one click instead of being cycled blindly through a single click-to-advance label.
- **The tab bar reads as part of the window, GNOME-native** — the dividing line under the tabs is repainted in the window's own background tone (and its contrasting shade dropped), so the tab bar blends into the content below it the way Nautilus' does, instead of being fenced off by a lighter rule. Theme-driven, so it follows light/dark and any installed theme pack.

## [0.23.0] - 2026-10-05

### Added
- **GNOME HIG sidebar/header redesign** — the window is now built as two real panels (sidebar + content), each with its own headerbar, the way GNOME Files and Settings are. The sidebar header carries a search toggle and a secondary "⋯" menu for the connection list itself (Select Connections, Sort Alphabetically, Sort by Recent Use); creating connections, the managers and import/export stay in the one primary menu. The content header carries the session actions and an optional group-path subtitle for the active connection ("Show hierarchy path in header", off by default). The protocol-filter pills collapse into one Filter button in the search row, which turns accent-coloured while a filter is on; the bottom toolbar is five direct icons. Window controls follow the system button layout and stay at the window edges whether the sidebar is shown or hidden, and fullscreen hides the sidebar together with the header and tab bar.
- **Vault read-only mode and search-from-root for every secret backend (issue [#353](https://github.com/totoshko88/RustConn/issues/353))** — Bitwarden, 1Password, Passbolt, `pass` and KeePass/kdbx each gained a "Read-only mode" and a "Search from vault root" toggle in Preferences → Secrets. Read-only refuses every write — save, delete, rename/move migrations, paste copies and credential transfers, in the GUI and in `rustconn-cli` — before any CLI runs, and the refusal is reported rather than routed around: a read-only vault is never silently replaced by the encrypted-file or keyring fallback. Search-from-root is read-widening and scoped-first, so credentials stored outside RustConn's own group are found without ever changing where writes land; outside that group an entry is matched by name, and when several entries in different folders share the name the first one found is used (the switch subtitle says so).
- **On-demand Cisco OpenH264 download for H.264 RDP GFX (issue [#262](https://github.com/totoshko88/RustConn/issues/262))** — packaged builds compile OpenH264 from source, which the loader refuses by SHA-256, so H.264 GFX silently fell back to a software codec. A new opt-in action (Settings → Connection → Media Codecs, plus `rustconn-cli codec download-h264`) fetches Cisco's official prebuilt blob over HTTPS on explicit consent (the dialog defaults to Cancel and links Cisco's binary licence), verifies its SHA-256, and installs it under the data directory — the Firefox pattern, so no patent-encumbered binary is redistributed. A "Use OpenH264" switch and a Remove button let it be turned off and back on or deleted without re-downloading, and it takes effect on the next RDP connection, no restart needed. The exact Cisco attribution appears in the Media Codecs row and in About.
- **Per-connection command macros and regex cluster auto-membership (asbru-borrow #1/#2)** — the Automation tab adds named single-line commands with a shortcut that types them into the terminal (pressing Enter unless "Run" is off) while that connection's terminal has keyboard focus — in a split tab, the focused pane's connection. `${username}`, `${host}`, `${port}` and your variables are filled in, a variable whose value is `@ask:` is asked for first, and `${password}` uses the password the connection was opened with; when none is available, or any reference is undefined, nothing is sent and a toast says why. Shortcuts need Ctrl, Alt or Super (F1–F24 may be used alone), may not reuse an application shortcut or another macro's, and are checked inline in the editor; commands may not contain line breaks or control characters. Macro shortcuts are inactive for RDP/VNC/SPICE/web sessions and while keyboard passthrough is on. A cluster can also auto-collect members by a regular expression matched anywhere in a connection's name or host (case-sensitive; `(?i)` ignores case), on top of or instead of ticked members: the cluster editor previews the match count as you type (also announced to screen readers), the cluster list and `rustconn-cli cluster list`/`show` count the resolved members (`show` marks pattern matches "(auto)"), and opening a cluster of more than ten members asks first, so an over-broad pattern such as `.` cannot open every connection at once.

### Changed
- **CI/release hardening** — tests run on `cargo-nextest`, a feature-powerset job and an advisory `cargo-semver-checks` job were added, caching moved to `Swatinem/rust-cache` behind a single `ci-success` gate, and every release now ships a `SHA256SUMS` manifest and an embedded dependency SBOM (`cargo auditable`).

### Fixed
- **YubiKey touch cue now fires on KeePass reads, not only writes (issue [#350](https://github.com/totoshko88/RustConn/issues/350))** — the three kdbx readers (connect, password load, root-search) were routed through the same chokepoint as writes, so the "touch your key" cue appears on every challenged read.
- **GFX frame accounting and H.264 fallback visibility (issue [#262](https://github.com/totoshko88/RustConn/issues/262))** — the frame-statistics counter is now fed from the real paint path (it was never recorded, so it read zero), giving the internal drop-rate diagnostics a real signal, and an RDP session now shows a toast (with an Open Settings button) when H.264 falls back to the software path instead of degrading silently.
- **The Welcome tab closes on the first real tab, not only the second** — the placeholder is now removed after the new page is appended and selected in every tab-creation path, so it never lingers beside the first session. It is recognised by a marker on its own page, not by its title, so a session tab that happens to be called "Welcome" (in any language) is never closed in its place.
- **Group Sync follows renames and moves on the Master, and rebuilds the nested hierarchy (issue [#263](https://github.com/totoshko88/RustConn/issues/263))** — a connection or subgroup renamed or moved on the Master is now renamed or moved in place on the Import side, keeping its id, its history and its vault credential, instead of being deleted and recreated. Import still gives every entity it creates an id of its own (the Master's copy can live on the same device, or reach it through Simple Sync), and records the Master's id in a new optional `sync_origin_id` field on connections and groups that it matches on first; trees imported by older versions are matched by name and path once and linked, and files without the field load unchanged. Subgroups are created at their real depth under existing groups — adding `Web/Prod` no longer creates a second `Web`, and a connection added to an existing subgroup no longer lands at the Import root — created groups keep the Master's description, icon and inherited settings, and a group name containing `/` stays one group. Everything is moved before anything is deleted, so a connection whose old group goes away is no longer stranded outside the Import group and recreated on the next sync, and KeePass and keyring entries follow sync-driven renames and moves of connections and groups (a read-only vault is logged and skipped). The GUI and `rustconn-cli sync import` now apply one shared plan from `rustconn-core` (`GroupSyncPlan`), so the CLI creates subgroups and applies renames and moves too, `rustconn-cli sync now` applies its imports instead of only reporting them, and sync reports count renamed or moved groups, so a sync that only renamed a group no longer prints "Already up to date".
- **A deleted or self-referencing jump host is detected instead of silently bypassed (issue [#345](https://github.com/totoshko88/RustConn/issues/345))** — when a Jump Host (the connection's own, a group's or the global one) names a connection that no longer exists, or the connection itself, the GUI now stops and asks before connecting without it ("Connect Directly", or "Connect Anyway" when a ProxyJump or the rest of the chain still applies; Cancel is the default), once per connection per session, and a cluster asks once for all its members. Only SSH, SFTP, RDP, VNC and SPICE are checked — the protocols that route through a jump host. The connection editor marks such a Jump Host row for SSH, RDP, VNC and SPICE until another is picked, and `rustconn-cli connect` prints a warning that the hop is skipped.
- **Import/export round-trip fixes** — CLI `export --format native` keeps templates/clusters/variables/snippets; Ásbrú import preserves the RDP domain and resolution and skips protocols that cannot round-trip; `.rdp` import preserves the three-way audio mode.
- **RDP: Multipath TCP and Kerberos NLA** — the MPTCP toggle now actually reaches the embedded client, `rustconn-cli add`/`update` can set Kerberos NLA + KDC address, and a Kerberos KDC proxy now reaches the external FreeRDP client too (as FreeRDP 3 `/kerberos:kdc-url:` for an MS-KKDCP `https://…/KdcProxy`), not just the embedded one (issue [#351](https://github.com/totoshko88/RustConn/issues/351)).
- **The stored password is sent to keyboard-interactive logins such as ESXi, not only to OpenSSH's own password prompt (issue [#364](https://github.com/totoshko88/RustConn/issues/364))** — the `SSH_ASKPASS` helper that releases a connection's (or jump host's) password matched only OpenSSH's `user@host's password:` form, so a server that authenticates through PAM keyboard-interactive — ESXi's `(root@host) Password:`, a plain `Password:` from a Dropbear or appliance — never received the password and the login fell through to `Permission denied`. The helper's matcher now mirrors the terminal-side one (`looks_like_password_prompt`): it accepts any account-password prompt, in the fifteen UI languages, while still staying silent for the prompts it must never answer — a key passphrase, a host-key confirmation, an OTP or verification code, a `sudo` prompt, and every stage of a password *change* (`old`/`current`/`new`/`retype`/`confirm`, including the Ukrainian and Russian forms), so the hardening behind issues [#191](https://github.com/totoshko88/RustConn/issues/191), [#254](https://github.com/totoshko88/RustConn/issues/254) and [#321](https://github.com/totoshko88/RustConn/issues/321) is preserved.
- **Config forward-compat marker now covers every config file** — history, tombstones, trash, snippets, clusters, templates and workspace profiles stamp the writing version and are backed up before an older version overwrites a newer file, including a save made without a prior load (such as `rustconn-cli history clear`). Downgrading to 0.22.15 drops a cluster's new `auto_membership` regex from `clusters.toml`; the file is backed up first, so re-upgrading restores it from the `.bak`.
- **Smaller fixes** — a split-pane scrollbar that could not be dragged (issue [#358](https://github.com/totoshko88/RustConn/issues/358)), a duplicated favorite on duplicate, a shared CLI-download checksum policy, the RDP/VNC Ctrl+Alt+Del toolbar button restyled from a filled block to a flat accent button to match the Shell button, and a session already shown in one split view is no longer offered in another's "Select Tab" (which could leave it visible in neither), with the move made atomic so a failed placement never strands it.

### Removed
- **"Color tabs by protocol" and "Show protocol filters" settings** — every tab already shows its protocol's symbolic icon, so the tab indicator only repeated it, and the protocol filters now live behind the sidebar's Filter button with nothing to keep shown. Both switches are gone from Settings → Interface; values saved by older versions are still read and kept, and simply have no effect.
